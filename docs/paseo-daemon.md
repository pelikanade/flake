# Paseo daemon

[Paseo](https://paseo.sh/docs.md) is a host for coding agents, terminals, projects,
workspaces, and schedules. Its standalone daemon runs on the host that should do
the work. Desktop, phone, browser, and CLI clients connect to that daemon to
dispatch tasks, follow progress, review changes, and answer agent permissions.
The repositories, provider executables, and build tools must exist on the daemon
host; connecting a client does not transfer its development environment. The
daemon declares omp's key-based providers and reads their keys from sops; it has
no interactive login, so Codex and Cursor stay desktop-only.

This aspect runs one standalone daemon per machine. It is independent of the
daemon bundled with Paseo Desktop and does not enroll the host in Paseo Hub.
Hub is a separate service for event-driven automations.

## Machine composition

Add `paseo-daemon` to the selected machine's aspect imports, preserving `base`:

```nix
imports = with inputs.self.modules.aspects; [
  base
  server
  sing-box
  paseo-daemon
];
```

Importing the aspect enables the service and declares its execution account,
which can run rootless containers of its own; that is a property of the account,
not of the daemon, which starts no container runtime and waits for none. A host
that should join the tailnet without sing-box needs its own `tailscaled` module,
which does not exist yet. Build that machine's NixOS configuration before
separately authorizing deployment:

```sh
nix develop
nix build .#nixosConfigurations.MACHINE.config.system.build.toplevel
```

If the host also runs Paseo Desktop's local daemon, give the standalone service
a different port to avoid a listener conflict. Set this in the consuming aspect:

```nix
systemd.services.paseo-daemon.environment.PASEO_LISTEN = "127.0.0.1:6768";
```

Use `ssh://USER@HOST?daemonPort=6768` for SSH transport and adjust the health probe
below. Commands selecting the service's `--home` follow its published endpoint.

The local `paseo-desktop` package pins the Paseo version, source hash, and npm
dependency hash directly in this flake. `paseo-daemon` inherits those values and
provides the `paseo` binary through its own headless package definition. Desktop
installs the complete unpacked Electron application generated by the upstream
electron-builder configuration. Both packages launch their daemons in production
mode, so the development-only mock providers do not appear, while preserving
the inherited `NODE_ENV`. The local packages include the server export in their
runtime closures and compile the terminal addon against Nix libraries. The
headless build includes the upstream web assets, but serving them remains
disabled by default.

## Systemd lifecycle and execution account

`paseo-daemon.service` starts at boot after `network-online.target`. It runs
`paseo daemon run` in the foreground as the unprivileged `paseo:paseo` account,
with a persistent home at `/var/lib/paseo` and `PASEO_HOME` at
`/var/lib/paseo/.paseo`. Systemd owns process lifetime, restarts failures after
five seconds, and stops the whole service cgroup, including agent and terminal
processes. `Type=simple` records process startup, not API readiness.

The service imports `omp` and installs its package set: omp with jq and Python.
Its PATH also includes Paseo, Bash, Git, SSH, Nix, and ripgrep. Additional project
tools belong in the consuming aspect's `systemd.services.paseo-daemon.path`, which
merges with the module's list. It does not inherit a desktop user's shell
environment or Home Manager packages, so the module installs devenv into the
system profile for the agents that run project dev shells; the workstation role's
devenv install stays with desktop users.

When sing-box is enabled, this consumer adds the `paseo` account and daemon unit
to the shared `sing-box` group. Human users join the same group through their
account module. It can read `/run/secrets/sing-box-api-key` and grants
full management access to the local sing-box API, including tailnet certificate
export. The [common API contract](sing-box.md#management-and-tailscale-certificate-api)
defines authentication and certificate export. Keep this credential out of
application processes and sandbox containers; host agents pass it only to the
sing-box CLI subprocess. Activating this group change restarts Paseo, so reconnect
before using it.

omp is the only installed agent provider Paseo can offer. The service runs upstream
omp and sets `PI_CONFIG_FILES` to an overlay that loads the packaged Magpie
extension, which reads the service account's NixOS-provisioned runtime credentials.

Systemd creates the home with mode `0700`; the service uses umask `0077`.
`ProtectHome=true` hides `/home`, `/root`, and `/run/user`, `ProtectSystem=full`
protects system configuration, and `NoNewPrivileges=true` prevents privilege
elevation. These restrictions also apply to agents and terminals. Clone projects
under `/var/lib/paseo/projects` or grant the `paseo` account access to another
explicit project directory outside the protected homes. Managed worktrees default
to `$PASEO_HOME/worktrees`. Private temporary files stay inside the service.

After deployment, inspect startup without printing pairing credentials:

```sh
systemctl status paseo-daemon.service
sudo -u paseo -H paseo --home /var/lib/paseo/.paseo daemon status --json
curl --fail http://127.0.0.1:6767/api/health
```

Use `journalctl -u paseo-daemon.service` for startup failures. The daemon also
writes `$PASEO_HOME/daemon.log`; redact credentials, pairing offers, and user code
before sharing either log. The pinned Paseo v0.11.2 exposes no Cursor provider in
its built-in manifest, and the built-in plugin providers it adds — Antigravity
(the `agy` CLI) and Muse Code (the `muse` CLI) — need their own signed-in
executables, which this host does not install.

The plugin reads `/var/lib/paseo/.omp/agent/magpie.yaml`. NixOS activation renders
only the endpoint and API key from `modules/secrets/magpie.yaml` and exposes the
template at that path, owned by `paseo` with mode `0400`; changes restart the
daemon. Systemd tmpfiles creates its parent directories before sops runs. Fill the placeholders
as described under [omp credentials](omp.md#credentials) before deployment.
The service does not generate omp's `config.yml` or share desktop OAuth logins.

Paseo ships its built-in omp provider disabled and owns `$PASEO_HOME/config.json`
for its own state, so enabling that provider is a manual change in that file,
outside this repository. Paseo drives omp over RPC (`omp --mode rpc-ui`), so
omp must be on the service's PATH. See [omp and its providers](omp.md).

Use `sudo systemctl restart paseo-daemon.service` for package, launch-environment,
or startup-setting changes. It interrupts running work. `paseo reload` can apply
runtime-safe configuration changes. Do not run `paseo daemon start` alongside
the service or use its stop command to manage systemd's lifecycle.

## Containers for agents

Paseo does not isolate its work in containers, and the daemon never talks to a
container runtime. The agents and terminals it hosts run as `paseo`, and those
processes may call `podman` or `docker` themselves. The account therefore has a
subordinate ID range (`autoSubUidGidRange`) and a lingering user manager, which
is what rootless Podman needs: the manager owns `/run/user/<uid>` and the socket
Podman serves there. Nothing else is granted, and container control is not
root-equivalent. A container started this way runs under `paseo`'s own uid and
reaches no more than the account can already read.

The repository runs containers rootless everywhere. The `podman` aspect enables
Podman without the rootful socket, or the `/run/docker.sock` symlink, that used
to front one shared daemon, so every account gets its own runtime and no account
can drive another's. Agents and other Docker API clients address that runtime
explicitly:

```sh
export DOCKER_HOST=unix:///run/user/$(id -u)/podman/podman.sock
docker info
```

The `podman` CLI needs no variable. That variable is the whole difference from
the retired Docker setup: the `docker` group is gone, and with it the ability of
a process holding it to control every container on the host. Keep agent workloads
out of host secrets, `$PASEO_HOME`, and broad host bind mounts anyway, since
`paseo` reads those itself; a rootless container sharing a host directory also
needs the account to reach it through its user namespace.

The account's runtime is also published on a fixed socket, which is what lets a
management UI drive it without that UI's container being able to read the
account's private runtime directory: `virtualisation.podman.runtimeApis.paseo`
declares the entry, and the account whose containers drive runtimes names itself
in `virtualisation.podman.runtimeApiClient`. See [the Portainer aspect](portainer.md),
which does that. Until such an account exists, the socket belongs to `paseo` itself
and is not reachable from another account's container.

A project that starts its own workload — a sandbox server, for instance — owns
that workload's runtime configuration. Bind its control API to loopback and keep
its key in a private runtime file. [Portainer](portainer.md) manages these
runtimes; on hosts that import it, the agents' runtime is one of its
environments.

Activation writes the subordinate IDs and starts the account's user manager. It
leaves the daemon alone unless the daemon unit's own settings changed.

From an administrator's normal session, inspect the Justfile and use the
repository's deployment recipe after building and reviewing the change:

```sh
nix develop -c just deploy
```

`deploy` runs `nh os switch .`. The `elevate` recipe runs
`pkexec /run/current-system/sw/bin/bash -c COMMAND`; it requires an administrator's
polkit authentication. Neither recipe can elevate a terminal inherited from
`paseo-daemon`: the service retains `NoNewPrivileges=true`, and no deployment
polkit rule is granted to `paseo`.

The server role already authorizes the maintainer's SSH key for root, and SSH
permits key-based root login on the tailnet. From a separate administrator's
session holding that key, deploy the prepared checkout in a detached system unit:

```sh
ssh root@neko-sphere 'systemd-run --unit=flake-deploy --collect --no-block --setenv=PATH=/run/current-system/sw/bin /run/current-system/sw/bin/nixos-rebuild --flake /var/lib/paseo/Projects/flake#neko-sphere switch -L'
```

The system manager owns this command, so a Paseo restart or SSH disconnect does
not terminate activation. Follow its result with
`ssh root@neko-sphere 'journalctl -u flake-deploy -f'`.

Use a reachable tailnet address if the host name does not resolve. Alternatively,
from an identical checkout on the administrator's machine, run
`nix develop -c just rdeploy neko-sphere root@neko-sphere`. Both SSH routes require
the already-authorized private key or a forwarded SSH agent and a verified host
key; they do not require changing sudo, polkit, or the Paseo service sandbox.

After the switch, check `systemctl status paseo-daemon.service` and run
`podman info` as `paseo` in a fresh process, then create, execute in, and delete a
container to confirm the account's runtime works. These are deployment checks,
not configuration-only guarantees.

## Connect after startup

The service binds `0.0.0.0:6767`: loopback for local clients and the host's
tailnet address for tailnet peers, admitted by the firewall only on `tailnet0`.
The password comes from `modules/secrets/paseo.yaml` through sops. Restrict 6767 with tailnet
grants. Set `systemd.services.paseo-daemon.environment.PASEO_LISTEN` back to
`127.0.0.1:6767` to keep it local. New Paseo homes start with relay disabled. The
runtime `config.json` stays writable and is preserved across restarts; the module
does not replace it or set `PASEO_RELAY_ENABLED`. This lets pairing persist its
explicit relay opt-in.

### Desktop and CLI over SSH

Use an existing SSH login to the host; the SSH account need not be `paseo`.
Paseo tunnels to the already-running daemon on remote localhost:

```sh
paseo --host ssh://USER@HOST ls -a
```

In Paseo Desktop, choose **Settings → Add host → Remote SSH** and enter the same
destination. SSH key authentication must already work non-interactively. SSH
transport does not install or start the daemon. No pairing offer or Paseo relay
is needed. See [Connectivity](https://paseo.sh/docs/connectivity.md).

### Phone or other clients through the relay

On the daemon host, run this deliberately as the service account, against its
home, after checking that it is reachable:

```sh
sudo -u paseo -H paseo --home /var/lib/paseo/.paseo daemon pair --relay
```

`--relay` explicitly enables the outbound relay without a confirmation prompt;
the daemon saves the choice and returns a QR code and pairing link. Scan the QR
code in the phone app, or choose **Paste pairing link**. After connecting through
SSH, Paseo Desktop's **Settings → your host → Pair a device → Enable relay** is
another way to do the same setup. The relay needs outbound connectivity but no
inbound port forwarding. Traffic is end-to-end encrypted; treat the offer as a
credential and keep it out of commits and logs. See [Security](https://paseo.sh/docs/security.md).

Always select this home: a bare pairing command as your desktop user selects
that user's daemon instead. A stopped home can produce an offline offer, so an
offer alone does not prove the service is healthy. The persistent daemon keypair
is generated at runtime under `PASEO_HOME`; preserve that directory to retain
host identity. Neither startup nor Nix activation generates or prints an offer.

To dispatch a task from a remote CLI through SSH, use a project path on the host:

```sh
paseo --host ssh://USER@HOST run --provider omp --cwd /var/lib/paseo/projects/PROJECT "Review the project"
```

The CLI also accepts a pairing link as `--host` for relay access. Keep it private
and avoid storing it in shell history. See the [CLI reference](https://paseo.sh/docs/cli.md).

### Direct access over the tailnet

The daemon already listens on the host's tailnet address, so a tailnet peer can
connect without SSH or the relay. A direct connection uses the password from
`modules/secrets/paseo.yaml`, and the tailnet carries it encrypted. Restrict 6767
with tailnet grants,
then add a **Direct connection** in the client with the host's tailnet name and
port 6767. Password authentication does not encrypt traffic, so keep it on the
tailnet rather than opening 6767 anywhere else.

Keep the daemon on loopback instead by setting
`systemd.services.paseo-daemon.environment.PASEO_LISTEN = "127.0.0.1:6767"` in the
consuming aspect and use SSH or the relay. A listener on another interface needs
that interface to exist before Paseo starts; add its service dependency there.

## Verification scope

Before use on a host, verify the service starts after reboot, the daemon's omp can
discover and run a model using the service account's configured credentials,
project permissions work for `paseo`, an SSH client can reach the API, and a phone can pair and reconnect
after a service restart. Confirm that stopping the service ends its agent and
terminal processes. Configuration evaluation and package builds alone cannot
prove these runtime behaviors.
